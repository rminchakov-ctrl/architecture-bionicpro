# Ключевые принципы предлагаемого решения

## Единая точка аутентификации (Identity Provider - IdP)
Все запросы на аутентификацию перенаправляются во внешний, доверенный Identity Provider (например, Keycloak). 
Это унифицирует доступ и позволяет гибко работать с разными провайдерами в разных странах.

## Backend For Frontend (BFF)
Специализированный сервис (BFF) обрабатывает все запросы от фронтенда. 
Он получает токены от IdP, но никогда не передаёт их фронтенду. Вместо этого он создаёт собственные, внутренние сессионные cookie. Это закрывает уязвимость, связанную с передачей токенов в браузер.

## Токены для межсервисного взаимодействия
Внутренние сервисы аутентифицируются друг с другом с помощью короткоживущих OAuth 2.0 access_tokens или взаимного TLS (mTLS), получаемых через сервисный аккаунт в IdP.

## Географически распределённое хранение данных
Базы данных пользовательских и медицинских данных (User Data DB, Medical Data DB) разворачиваются в регионах присутствия (например, в РФ, ЕС, США). 
Это обеспечивает соблюдение GDPR, HIPAA и других локальных регуляториев. IdP и сервис авторизации (Policy Decision Point) управляют политиками доступа к этим данным.

## Специализированные хранилища
Используется правочный инструмент для аналитики и отчетов (ClickHouse), который синхронизируется только с необходимыми данными через ETL-процесс.

# Про архитектуру

## Унификация доступа и безопасная схема работы с токенами
- Роль BFF: Сервис BFF выступает единственным посредником между фронтендом и бэкендом.
- - Вход: Пользователь пытается войти через фронтенд -> фронтенд перенаправляет его на BFF -> BFF перенаправляет в нужный внешний IdP (выбор IdP может определяться по домену пользователя или геолокации).
- - Сессия: После успешной аутентификации в IdP, тот перенаправляет пользователя обратно в BFF с кодом авторизации. BFF напрямую (сервер-сервер) обменивает код на id_token, access_token и refresh_token.
- - Ключевой момент: BFF проверяет id_token, создает сессию для пользователя и отправляет в браузер только зашифрованную сессионную cookie (httpOnly, secure, SameSite=strict). Сами токены IdP хранятся в памяти BFF и никогда не покидают серверную часть.
- - Обновление: Когда access_token протухает, BFF использует свой refresh_token для его обновления, абсолютно прозрачно для пользователя и фронтенда.

## Управление учётными данными и авторизация
- User Data DB: Хранит идентификаторы пользователей (например, user_id), их роли и связи с протезами (user_id <-> prosthesis_id). Это критично для авторизации.
- Сервис Авторизации (Policy Decision Point): Этот сервис определяет, имеет ли пользователь право на доступ к запрашиваемому ресурсу. BFF при каждом запросе (например, "скачать отчет для prosthesis_id=123") спрашивает у этого сервиса: "Имеет ли user_id X доступ к prosthesis_id Y?".
- Логика принятия решения: Сервис авторизации проверяет права доступа, сверяясь с User Data DB. Это гарантирует, что пользователь видит данные только своих протезов.

## Поддержка multiple IdP и географическое разделение данных
- Внешний IdP: На диаграмме он один, но на практике их может быть несколько (например, отдельный для РФ, отдельный для EU). BFF и сервис авторизации должны быть сконфигурированы для работы с каждым из них.
- Локальное хранение: Медицинские данные (Medical Data DB) физически расположены в регионах. Сервис отчетов, обрабатывая запрос, обращается к локальной для своего региона базе медицинских данных. Данные пользователей (User Data DB) могут храниться централизованно или также распределённо, с репликацией только необходимых для авторизации данных (например, mapping user_id -> prosthesis_id).

## Генерация отчетов
- ClickHouse: Используется для быстрой агрегации данных для отчетов. ETL-процесс (на диаграмме не показан) будет периодически переносить агрегированные и обезличенные данные из операционных БД (PostgreSQL) в ClickHouse.
- Сервис Отчетов: Получает авторизованный запрос от BFF, запрашивает сырые данные из Medical Data DB и агрегированные данные из ClickHouse, формирует финальный отчет и возвращает его пользователю через BFF.

## Программа в чипе протеза (Prosthesis)
- Связь: Протез не взаимодействует с системой напрямую. Он соединяется с Мобильным приложением по безопасному каналу (например, Bluetooth). Приложение выступает шлюзом, который перенаправляет необходимые запросы в BFF от имени пользователя. Это упрощает безопасность и управление подключениями.
- Данные: Данные о работе протеза, собираемые программой, через приложение попадают в Medical Data DB.

## Приложение для донастройки протеза (Mobile App Frontend)
- Роль: Это единственный фронтенд-клиент, с которым взаимодействует пользователь. Он отвечает и за настройку протеза, и за запрос отчетов, и за вход в систему.
- Связь: Все API-вызовы идут через BFF, который обеспечивает единую точку входа, аутентификацию и авторизацию.

## Интернет-магазин (Store Service & DB)
- Роль: Отдельный сервис, отвечающий за каталог продукции, корзину, оформление заказов и т.д.
- Интеграция: Для работы ему нужны данные о пользователе (из User Data DB через AuthSvc) и, возможно, информация о протезах клиента (из CRM Service), чтобы предлагать совместимые аксессуары. Платежные и товарные данные хранятся в своей Store DB.

## CRM (CRM Service & DB)
- Роль: Ключевой сервис для управления клиентами, историями заказов, поддержки.
- Интеграция: Является основным источником правды о клиентах и их заказах. Именно данные из CRM DB должны синхронизироваться с ClickHouse для формирования отчетов (например, о том, какой протез у какого клиента). Сервис отчетов (ReportSvc) обращается в CRM, чтобы понять, к каким данным пользователь имеет доступ.

# Как решаются изначальные проблемы в этой архитектуре
- Утечка данных: Вся аутентификация вынесена на внешний IdP. Внутренняя система не хранит паролей. BFF pattern предотвращает утечку токенов.
- Запрос отчетов: Реализован отдельным сервисом (ReportSvc), который агрегирует данные из Medical Data DB и ClickHouse. Права доступа к отчету проверяются через AuthSvc, который сверяет user_id с prosthesis_id из CRM DB.
- Объем данных: Операционные данные хранятся в PostgreSQL, а для отчетов и аналитики используется оптимизированный ClickHouse. Это снимает нагрузку с основных БД.
- Выход на новые рынки: Географически распределенные Medical Data DB и возможность подключения нескольких внешних IdP позволяют соблюдать требования GDPR, HIPAA и других локальных нормативных актов.

# Выводы:
Предложенная архитектура решает поставленные задачи:
- Безопасность: Исключает утечку токенов IdP, изолирует фронтенд от прямого доступа к бэкенду.
- Унификация: Единый интерфейс (BFF + внешний IdP) для всех типов клиентов и провайдеров.
- Масштабируемость: Легко добавлять новые внешние IdP для новых рынков.
- Соответствие регуляторам: Обеспечивается за счет географической привязки данных к хранилищам.
- Производительность: Разделение БД для операционных и аналитических задач решает проблему с "огромным объемом данных".
