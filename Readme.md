## Замечания
### Магия Nginx
Блок http. Основной блок для конфигурации HTTP-сервера.
- Директива proxy_cache_path. Это сердце кэширования. Она задаёт путь и параметры кэша.
- - /var/cache/nginx: Физический путь на диске внутри контейнера, где будут храниться кэшированные файлы.
- - levels=1:2: Определяет структуру поддиректорий для хранения кэшированных файлов (1 символ + 2 символа). Ускоряет доступ в файловых системах с большим количеством файлов.
- - keys_zone=reports_cache:10m:
- - - reports_cache — название зоны, к которой будут обращаться другие директивы.
- - - 10m — выделяет 10 **мегабайт** оперативной памяти под метаданных кэша (ключи, параметры истечения срока действия). Этого объема хватит примерно на 80 тысяч ключей.
- - max_size=1g: Максимальный размер всего кэша на диске. 1g = 1 гигабайт. При достижении лимита Nginx удалит файлы, к которым дольше всего не было обращений.
- - inactive=24h: Файл в кэше, к которому не обращались 24 часа, будет удалён, даже если он не протух.
- - use_temp_path=off: Рекомендуемая настройка для записи временных файлов напрямую в кэширующую директорию - исключает лишнее копирование данных между дисками.
- Блок upstream. Определяет группу серверов, на которые Nginx будет проксировать запросы.
- - server minio:9000: Указывает адрес и порт сервера MinIO.
- Блок server. Видит трафик на порту 80 и определяет, как его обрабатывать.
- - Локация location /reports/. Самая важная часть конфига, которая и реализует кэширующий CDN.
- - - proxy_cache reports_cache;: Включает кэширование для этой локации и указывает на зону reports_cache, которую мы объявили в proxy_cache_path.
- - - proxy_cache_valid 200 12h;: Кэшируй ответы с кодом 200 на 12 часов.
- - - proxy_cache_valid 404 1m;: Кэшируй ответы 404 на 1 минуту.
- - - proxy_cache_use_stale: Определяет, когда можно отдать устаревший (stale) кэш, если бэкенд не доступен. Очень полезная настройка для отказоустойчивости.
- - - proxy_cache_background_update on;: Позволяет Nginx выпустить устаревший кэшированный ответ клиенту немедленно, а затем асинхронно обновить его с бэкенда. Это ускоряет отдачу контента.
- - - proxy_cache_lock on;: Если несколько запросов приходят на один и тот же некэшированный URL, включается лок. Только первый запрос пойдёт в бэкенд, остальные будут ждать его результата и использовать его. Защищает бэкенд от шарахания.
- - - proxy_cache_key: Определяет, что составляет уникальный ключ кэша. Используется схема, метод, хост и URI.
- - - add_header X-Cache-Status $upstream_cache_status;: Очень полезный заголовок для дебага. Показывает: HIT, MISS, EXPIRED, etc.
- - - add_header Cache-Control "public, max-age=43200";: Директива, которую Nginx сам добавит в ответ клиенту, говоря браузеру или промежуточным кэшам: ты тоже можешь кэшировать этот ответ на 12 часов (43200 секунды).
- - - proxy_pass http://minio/;: Собственно, команда "проксировать запрос на upstream-группу с именем minio".
- - - proxy_set_header Host $host;: Корректно пересылает исходный заголовок Host в MinIO, что крайне важно для доступа в стиле виртуального хоста (который MinIO использует для доступа к хранилищам).
- - Локация location /health. Простой эндпоинт для проверки здоровья самого Nginx, который всегда возвращает 200. Полезен для балансировщиков нагрузки или оркестраторов.

Как это работает:
- Первый запрос на http://nginx/reports/mybucket/myreport.json приходит в Nginx.
- Nginx проверяет его по ключу (proxy_cache_key) в зоне reports_cache.
- Кэш пуст (MISS), запрос проксируется на minio:9000.
- Ответ от MinIO сохраняется в кэш на диске (/var/cache/nginx) и отдается клиенту.
- Следующий запрос на этот же URL.
- Nginx находит ответ в кэше (HIT) и сразу отдает его клиенту, не обращаясь к MinIO.
- Через 12 часов (proxy_cache_valid) запись считается устаревшей. Следующий запрос запустит фоновое обновление данных с MinIO (proxy_cache_background_update).

### Магия Debezium в PostgreSQL
- Включение логической репиликации [скриптом](./crm-db/init-replication.sql)
- - пользователь БД (crm_user) должен иметь права REPLICATION:
```sql
ALTER USER crm_user WITH REPLICATION;
```
- Регистрация Debezium Connector [скриптом](./connectors/crm-postgres-connector.json)
- После этого Debezium начинает следующую последовательность действий:
- - подключается к PostgreSQL по указанным параметрам.
- - использует слот репликации debezium_slot для отслеживания изменений.
- - читает данные из публикации debezium_publication.
- - преобразует изменения (INSERT/UPDATE/DELETE) в события Avro/JSON.
- - отправляет события в указанный топик Kafka (crm-db-server.public.customers).
- Проверка статус коннектора
``` bash
curl -s http://localhost:8083/connectors/crm-postgres-connector/status | jq .
```

### Магия KafkaEngine в ClickHouse
- Таблица-интерфейс для Kafka (виртуальная) kafka_customers, магия в ENGINE = Kafka, где:
- - 'kafka:9092' - брокер
- - 'crm-db-server.public.customers' - топик
- - 'clickhouse-consumer-group' - группа потребителей
- - 'JSONEachRow' - формат данных
- При получении новых сообщений из топика crm-db-server.public.customers:
- - они автоматически появляются в этой таблице в виде строк.
- - поля _key, _topic, _partition, _offset — это стандартные метаданные сообщения Kafka.
- - поля op, before, after — это данные, которые формирует Debezium при обработке изменений из PostgreSQL.
- Целевая таблица для данных - customers_cdc - настоящая таблица ClickHouse, где будут храниться конечные, очищенные данные.
- Materialized View — customers_cdc_mv - работает как непрерывный трансформатор:
- - слушает таблицу kafka_customers.
- - как только в нее поступает новая строка (сообщение из Kafka), запускается запрос SELECT ... FROM kafka_customers.
- - результат этого запроса автоматически вставляется в целевую таблицу - customers_cdc.
